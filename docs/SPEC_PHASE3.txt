FEATURE A — AMBIENT LISTENING / MICROPHONE PASSTHROUGH

Goal: Capture environmental audio and reproduce it through the connected headphones, optionally mixed with music where technically feasible.

A1. Headphone microphone route
- Detect connected audio devices and inspect whether the HD 4.50BTNC Bluetooth microphone is available as an input.
- Investigate Android AudioRecord, AudioManager communication routing, Bluetooth SCO/HFP, supported audio device types, and current OS restrictions.
- Use documented APIs and device capability checks. Do not assume Bluetooth input and high-quality music playback can coexist.
- Determine whether selecting the headset microphone forces HFP/call mode, degrades music quality, pauses media, or creates unacceptable latency.
- Never silently change the user's system audio route without explaining it and providing a clear stop/restore action.
- Use the least intrusive supported routing approach; avoid unnecessary phone-call UI or telecom APIs.

A2. Phone microphone fallback
- If headset-microphone passthrough is unavailable or unsuitable, implement an optional phone-microphone mode.
- Explain that the phone mic hears the environment near the phone, not at the wearer's ears.
- Show the active input device and current route clearly.
- Do not falsely claim headset-microphone input when the phone microphone is being used.

A3. Real-time audio engine
- Build a dedicated, lifecycle-safe audio engine on a suitable low-latency path, using AudioRecord and AudioTrack or another justified supported mechanism.
- Select supported sample rates and buffer sizes dynamically. Avoid arbitrary fixed settings that only work on one device.
- Implement a clean start/stop lifecycle, cancellation, resource release, error recovery, and Bluetooth disconnect handling.
- Prevent feedback loops, clipping, DC offsets, runaway gain, and unbounded buffering.
- Add conservative gain limits and a peak limiter. Start at a safe low gain; never automatically boost loud environmental sound to high levels.
- Do not write microphone samples or environmental audio to persistent storage.
- Handle audio focus and media playback carefully. Do not promise seamless music mixing until verified.
- Measure and document actual input-to-output latency where possible. Explain how to run the manual measurement.
- If low-latency monitoring cannot be achieved on the available route, show a clear unsupported/experimental status rather than pretending success.

A4. Ambient UI
- Add an Ambient tab or a coherent Ambient Mode section consistent with the existing navigation.
- Provide an explicit Start/Stop control.
- Add an ambient gain/volume slider, a numeric indication (dB or normalized percentage, correctly labeled), and a mute control.
- Show microphone permission state, selected input device, output device, connection state, and any HFP/call-quality limitation.
- Provide concise safety messaging: ambient playback is not hearing protection and must not be relied upon for traffic awareness.
- Stop capture immediately when the user presses Stop, revokes permission, disconnects the device where appropriate, or the service is terminated.
- If background operation is supported, use the appropriate foreground service type and visible notification according to the target Android version. Do not run covertly.
- Ask for microphone permission only when the user activates the feature, not at initial launch.
- Do not request unrelated permissions.

A5. Ambient acceptance tests
- Test phone microphone capture and output independently of Bluetooth input.
- Test Bluetooth headset microphone selection and record the actual route.
- Check whether music continues and whether audio quality changes when passthrough starts.
- Test start/stop repeatedly, denied permissions, Bluetooth disconnection, app backgrounding, and resource cleanup.
- Clearly distinguish code-compiles, unit-tested, and physically tested behavior. Do not claim hardware validation unless it occurred.

FEATURE B — SYSTEM-WIDE EQUALIZER

Goal: Apply the existing 10-band EQ to eligible playback from external applications, including Spotify, instead of only audio rendered by AfterTune.

B1. Research and architecture
- Investigate Android AudioEffect/Equalizer APIs, audio session routing, global output-mix restrictions, current target SDK behavior, and viable non-root architectures.
- Research SoundID's documented Android behavior as a reference, but do not assume its proprietary implementation or claim it uses a specific mechanism without evidence.
- Consider Android audio-effect sessions, OEM-supported effects, compatible audio-effect integrations, and other legitimate mechanisms. Do not assume that an AccessibilityService, microphone capture, playback capture, or a foreground service alone can apply DSP to other apps' output.
- Do not use microphone loopback as a substitute for system-wide EQ.
- Do not claim universal system-wide processing if the chosen implementation only affects selected apps, particular sessions, or certain Android versions.
- Do not root the device, exploit security boundaries, or require privileged/system-app permissions that a normal installed app cannot obtain.
- Keep the existing in-app EQ fully functional.

B2. Implementation
- First implement the strongest technically supported approach that works as a normal installed application.
- If a supported global audio-effect path exists, wire the current 10-band EQ settings and presets into it.
- If a system effect requires OEM support or an external integration, detect and explain the requirement instead of presenting a fake toggle.
- If Android does not expose a viable general solution for this device, do not fabricate one. Provide a short evidence-based report of tested approaches, exact limitations, and the next practical experiment.
- Avoid writing a custom virtual audio device or claiming that ordinary Android apps can transparently intercept all other apps' playback without a valid supported mechanism.
- Ensure the EQ has a clear enabled/disabled state that reflects actual backend status.

B3. System-wide EQ acceptance tests
- Test with Spotify playing externally while the app is backgrounded.
- Change a single EQ band substantially and confirm an audible difference in Spotify.
- Compare enabled/disabled output and confirm the effect is not merely affecting AfterTune's own player.
- Verify presets, preamp/headroom, clipping control, and interaction with existing OEM EQ effects.
- Record device model, Android version, route, mechanism, and exact limitations.
- If the physical Spotify test cannot be performed, label it NOT VERIFIED and give the user precise test steps.
